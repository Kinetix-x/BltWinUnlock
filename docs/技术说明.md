# 技术说明

写给要读代码或改代码的人。这里只留「不知道就会踩进去」的东西，每条都注明了症状——因为这类 bug 的特征
是**不报错、只是不工作**。

---

## 1. 三层结构

```
btwu tray / run（交互用户，计划任务在登录时拉起）
        │  每 10 秒兜底轮询 + 蓝牙事件
        ▼
%ProgramData%\BtwuUnlock\presence.dat      ← 一行文本：BTWU1|present|since|heartbeat|...
        │  （agent 发布，凭据提供程序只读）
        ▼
BtwuCredProv.dll （在 LogonUI 进程里，锁屏时加载）
        │  GetCredentialCount / GetSerialization
        ▼
LSA —— 口令校验与解锁
```

关键事实：**凭据提供程序自己查不了蓝牙**（它在 LogonUI 进程里，不该做射频操作、也拿不到设备句柄）。
它只能读 agent 发布的状态文件，所以「在场检测」不能只在锁屏时做。

## 2. 凭据提供程序的七个硬约束

| # | 约束 | 违反时的症状 |
| --- | --- | --- |
| 1 | `GetSerialization` 里的 `MessageType` **跟随场景号**，不跟随「这是一次解锁」：`CPUS_UNLOCK_WORKSTATION(2)→7`、`CPUS_LOGON(1)→2` | 锁屏报「用户名或密码不正确」，日志 `0xC000006D / 0xC00000E5`。⚠️ `0xC00000E5` 是 `STATUS_INTERNAL_ERROR`，**不是**口令错——msg=7 要求 LSA 解锁 `LogonId` 指明的会话，而它故意留 0 |
| 2 | 从 Windows 10 起锁屏用 `CPUS_LOGON(1)` 送进来，所以**两个场景都要接**；收到 `1` 时用 `WTSQuerySessionInformation` 判断本会话有没有登录用户 | 真登录界面也去解锁（或锁屏直接拒绝） |
| 3 | `CPUS_CREDUI` **永远拒绝** | 保管的口令能静默通过 UAC 提权框 |
| 4 | `GetUserSid` 返回的 SID 必须是**本会话用户的账户 SID** | 返回一个本机不存在的 SID（典型：MSA 身份 SID `S-1-11-96-…`）会让磁贴挂不上任何用户——锁屏只剩壁纸，连密码框都没有 |
| 5 | **绝不**声明 `pbAutoLogonWithDefault = TRUE` 却交不出凭据 | LogonUI 会立刻对默认磁贴调 `GetSerialization`，失败即卡在「等提交」。所以默认是「回车模式」，且**载荷在 `GetCredentialCount` 里就预构建完**（解密 + 打包 + 缓存），`GetSerialization` 只做 memcpy |
| 6 | 磁贴里必须有**一个可聚焦且可编辑**的字段 | 全是不可编辑字段（`CPFIS_FOCUSED` 不允许用在不可编辑字段上）时没有任何字段能接住回车，用户只能用鼠标点那个右向箭头。做法：加一个空的 `CPFT_EDIT_TEXT`，`GetSubmitButtonValue` 指向它，`SetStringValue` 对它返回 `S_OK`（返回 `E_NOTIMPL` 会让 LogonUI 视为只读、焦点丢失） |
| 7 | 任何异常路径都 **fail closed**：返回错误 + 0 个凭据 | 把锁屏弄坏（最坏情况：整个登录界面失去 UI）。`GetCredentialCount` 与 `GetCredentialAt` 必须共用同一个判断 |

## 3. 「在场」只有一个含义

`presence.dat` 里的 `present` 表示**触发设备此刻连着吗**，**没有任何宽限**。

它一度同时回答两个互相冲突的问题：「用户走了吗」（需要宽限，BLE 键盘打盹 ≠ 人走了）与
「设备此刻连着吗」（一秒都不能宽限）。混用的后果是一次真实的实测事故：键盘断开后的 45 秒里，
锁屏仍然提供了凭据并成功解锁——**键盘不在屋里，机器自己解了**。

现在的分工：`RawConnected`（**发布值，无去抖**）用于凭据提供程序判断是否放行；`Present`（去抖）
只在 agent 进程内用于「要不要锁屏」（默认关闭）。改宽限期语义前先想清楚在改哪一个。

## 4. 账户登录形式必须问 Windows

Windows 账户有两种形式，**不同的主体**：

```
本地账户        .\alice  /  DESKTOP-A1B2C3\alice        → S-1-5-21-…
Microsoft 账户  MicrosoftAccount\alice@example.com      → S-1-11-96-…
```

形式填错时，`LogonUser` 与 LSA 都只回 `ERROR_LOGON_FAILURE (0x52E)`——它**分不出**「口令错」
「账户名不存在」「形式错」。所以：

- 判据用 `NetUserGetInfo(level 24).usri24_internet_identity`（与 `Get-LocalUser` 的 `PrincipalSource` 同源）：
  `False` ⇒ 就是本机账户形式，注册表一概不看；
- `HKCU\…\IdentityCRL\UserExtendedProperties` 里的邮箱**只是线索**——它记的是「这个用户拿哪个微软账户
  登录过 Store / Office / Edge」，在有残留项的**本地账户**机器上会把域定成 `MicrosoftAccount`；
- 查不出来（API 失败）时**保持保守兜底，不要当成「本地账户」**，否则会静默降级一台真的 Microsoft 账户机器；
- 录入时**两种形式各问一次**，谁被接受就用谁，并把「试过什么」逐条打印出来。

另一个必须分开的概念：「喂给 LSA 的登录名」与「进程自己的账户」。录入是提权子进程，
「回应 UAC 的账户」不保证是「锁屏要解锁的那个账户」——备用形式要用
`WTSQuerySessionInformation` 取**交互会话**的账户。

## 5. 状态发布的原子性

`presence.dat` 每 10 秒（或事件触发）被重写。写者与读者必须遵守：

- 写：临时名**含 pid + 线程 id**，`MoveFileEx(REPLACE_EXISTING)`，失败重试，最后兜底就地覆盖；
- 读：一律 `FileShare.ReadWrite | Delete`。
  `MoveFileEx` 需要源和目标都有 delete 权限，任何只带 `FILE_SHARE_READ` 的持有者
  （`.NET` 的 `File.ReadAllText` 就是）都会让它以 `ERROR_ACCESS_DENIED` 失败；
  **共用的临时名实测能让目标文件消失**。

发布通道本身**永不抛异常**（返回 `bool`），失败时不推进签名以便下一拍重试；安全关键路径上的常驻循环
必须逐次 try/catch + 退避 + 限流告警，**只有取消异常可以退出**——一次未捕获的异常会让「服务在跑、
功能没了」，而这个观察会骗过所有人。

## 6. 界面布局：三个反直觉的事实

本机实测环境是 200% 缩放（DPI 192）。WinForms 在这里有一处致命的不对称：

1. **控件默认尺寸会随 DPI 缩放，手写的尺寸不会**。`new Button{Text=…}` 会以 2 倍高出现，
   而 `Height = 48` 仍是 48 物理像素——一碰就把按钮切成两半。所以窗口用
   `AutoScaleMode.None` + 自己的 `Ui.Px()` 缩放 + 容器/按钮一律 `AutoSize`；
2. **`AutoSize` 行的首选高度是一条循环测量的链**（父 AutoSize ⇄ 子 `Dock=Fill`），
   WinForms 只能用当前尺寸解一次，于是**同一份代码可能量对、也可能塌掉**。
   列表这类没有自然高度的控件，行高必须用 `SizeType.Absolute` **钉死**，不要让它经过那条链；
3. `Dock=Fill` 与 `Dock=Top/Bottom` **不要叠在同一页**（Fill 会吃掉整个客户区，横幅盖住第一行）。
   窗口被压到工作区以内时，内容要能**滚动**（`AutoScroll` 面板），否则「内容比窗口高」会表现成
   「按钮被切一半、够不着」。

## 7. 非模态窗口上的 `DialogResult` 是哑的

```csharp
Application.Run(form);                    // 非模态
var cancel = new Button { DialogResult = DialogResult.Cancel };
// 点下去：Click 事件确实收到、DialogResult 变成 Cancel，但**窗口不关**
```

实测过两个方向（真实鼠标点击 + `PerformClick`）。所以对话框一律用 `ShowDialog()`，
「取消/关闭」再挂一句显式 `Close()` 作双保险。

**同一个窗口的多条打开路径必须一致**——本项目就有一个窗口（录入对话框）被面板以非模态打开、
被安装流程以模态打开，于是「取消点了没反应」只在一条路上出现，人工测试永远碰不到。

## 8. 发包前的卫生扫描

要发布的包里不能有构建机信息，也不能有「假设自己在哪儿」的东西。已修过的四类：
dll 里嵌着构建机的 pdb 路径（用 `Directory.Build.props` 的 `PathMap` 重写成 `/btwu/`）、
帮助文本里写了真实账号、脚本里印裸相对路径、绿色版用 `.lnk`（只能存绝对路径，一移动就失效）。

规矩是**逐文件、UTF-8 与 UTF-16LE 各扫一遍**（`grep` 对 .NET 的 UTF-16 字符串是瞎的），
**绝不 `| head`**（第一版扫描就是这样「通过」的，命中行被截掉了）。工具见 `tools/hygienescan`。

## 9. 判据要能失败

这个项目不接受「只能通过」的检查：

- `harness.exe` 59 条断言、`tools/statetest --naive` 跑旧实现**并要求它抛异常**；
- `btwu --gui-selftest` 里有一条是「复刻旧写法，要求它关不掉窗」；
- 卫生扫描器先在**已知会失败的输入**上跑一次，再去信它的「0 命中」；
- 断言还要**量对对象**：曾有一条「设备列表高度 ≥ 120」在 bug 存在时照样全绿，因为塌的不是列表自己，
  而是装它的那个框——判据要写成「框装得下列表」。

## 10. 与锁屏同路的验证

`btwu verify` 用**网络登录类型**与场景无关的消息类型，真实锁屏用**交互登录类型**与场景决定的消息类型——
两者能得出相反结论。分工：`verify` 管「口令与打包格式」，`btwu unlock-probe` 管「锁屏那一刻的提交」
（需管理员：交互登录要求 `SeTcbPrivilege` + `SeIncreaseQuotaPrivilege`）。冲突时以后者为准。
